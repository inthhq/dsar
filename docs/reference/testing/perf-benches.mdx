Default `bun run test` does not run these jobs. They are opt-in so a 10k-request
by 1k-event matrix never lands on every pull request.

## How to run

```sh
bun run bench
```

That sets `PERF=1` and runs the package `bench` scripts through Turborepo.
You can also run one package:

```sh
PERF=1 bun run --cwd packages/backend bench
PERF=1 bun run --cwd packages/internals/persistence bench
PERF=1 bun run --cwd packages/internals/policy-packs bench
```

CI runs the same command on `main` via `.github/workflows/bench.yml`. It is
not a required pull-request check.

## What is measured

All benches use `@effect/vitest` `it.effect` (TestClock) and in-memory
stores. Bounds are p95 over 40 samples after 5 warmups, except the policy
upgrade path, which is one propose/approve/apply after the catalog is loaded.

| Path | Fixture | Bound | Measured on a local Bun 1.3.14 run |
| --- | --- | --- | --- |
| `computeLegalClock` | 512 timeline events | p95 under 50ms | p95 0.19ms |
| `listBySubject` | 1,000 SQLite `:memory:` rows with the subject index | p95 under 100ms | p95 0.21ms |
| Policy pack `diff` | 100 published versions | p95 under 50ms | p95 0.012ms |
| Policy upgrade propose/approve/apply | 100 published versions | under 1s | 0.45ms |

100 packs is enough to finish in well under a second on this machine, so the suite
keeps that count instead of shrinking it.

The existing SQLite one-shot scale test in
`packages/internals/persistence/test/persistence.test.ts` still runs on every
PR. It is a correctness bound on the index, not this p95 suite.

Clock numbers apply to in-process recompute, the same function behind
`GET /requests/:id/clock/explain`. Subject numbers apply to indexed
`listBySubject`, the lookup behind `GET /subjects/:subjectId`.
