`@dsar/react` is the UI kit. It does not own login. That matches the [auth model](../architecture/auth-model.md): the host authenticates, DSAR sees a projected identity.

## Hosted (inth.com)

```tsx
import { DsarProvider, SubjectPortal, hosted } from "@dsar/react";

<DsarProvider mode={hosted({ url: "https://acme-prod.inth.app/dsar" })}>
	<SubjectPortal />
</DsarProvider>
```

Pass the full origin (`https://org-project.inth.app/dsar`). Webhooks use that same origin. Cookies stay on inth.app. Do not put `DSAR_API_TOKEN` in the browser.

## Local self-host

Run kitchen-sink as the DSAR HTTP server. The Next examples are UI only.

```tsx
import { DsarProvider, SubjectPortal, selfHosted } from "@dsar/react";

<DsarProvider
	mode={selfHosted({ url: "http://kitchen-sink.localhost:1355/api/v1" })}
>
	<SubjectPortal />
</DsarProvider>
```

```sh
bunx turbo run dev --filter=dsar-kitchen-sink-example --filter=dsar-subject-portal-example --filter=dsar-dashboard-example
```

- Backend: `http://kitchen-sink.localhost:1355/api/v1`
- Subject portal: `http://localhost:1356`
- Operator queue: `http://localhost:1357`

Kitchen-sink SQLite is the default store (`DSAR_PERSISTENCE_DRIVER=pg` for Postgres). In development it CORS-allows those UI origins and maps `Origin` to a demo subject or operator identity. CLI and SDK keep using bearer tokens.

## Docker Postgres

```sh
DSAR_PERSISTENCE_DRIVER=pg DSAR_PERSISTENCE_PG_URL=postgres://postgres:postgres@localhost:5432/dsar bunx turbo run dev --filter=dsar-kitchen-sink-example
```
