These notes are for the published `dsar` package line, from npm `0.0.5` to
`1.0.0`. The next version cut is `1.0.0`. Apply them when you install
`dsar@1.0.0`.

Tenant policy-pack pin and apply is a different workflow. See
[Policy Versioning and Upgrades](../architecture/policy-versioning-and-upgrades.md).
SQL schema history lives in
[Tenant-Safe Persistence](../architecture/tenant-safe-persistence.md).

Release bullets stay in `packages/dsar/CHANGELOG.md`. This page is the
migration path those bullets do not spell out.

## Summary

`1.0.0` is a major because the runtime line moved and an unsupported umbrella
export went away.

- Node.js 24 is required (`engines.node` is `>=24 <25`).
- Application code compiles with TypeScript 7.
- Runtime Effect packages are `4.0.0-beta.101`.
- `dsar/adapter-c15t` is gone. Use a supported inbound adapter or leave inbound
  unconfigured.
- The persistence-backed Chat SDK state adapter now stores transcript lists,
  message queues, and force-unlock state for Chat SDK 4.34.

`1.0.0` also adds webhook receiver middleware, outbound dispatch listing and
replay, `dsar doctor` / `GET /status/diagnostics`, and Unkey fail-closed
verification. Those are compatible additions. The Unkey change matters if you
treated a thrown `verifyKey` as something other than an unauthenticated
request.

## Breaking changes

**Node 24.** Hosts on Node 22 or earlier will not satisfy `engines`. Use Node
24.x. The repo pins `24.18.0` in `.node-version`.

**TypeScript 7.** The workspace compiles with TypeScript `7.0.2`. If you
typecheck against DSAR public types, move onto TypeScript 7. HTTP-only callers
that never compile those types can skip this.

**Effect 4.** Keep `effect`, `@effect/platform-*`, `@effect/sql-*`, and
`@effect/vitest` on `4.0.0-beta.101`. Mixing Effect 3 with this runtime will
fail typecheck or fail at the layer boundary.

**Removed `dsar/adapter-c15t`.** The umbrella package no longer exports
`dsar/adapter-c15t`, and the private `@dsar/adapter-c15t` workspace package is
not in this repo. Published `0.0.5` already omitted that subpath. `0.0.4` still
had it. Delete any remaining `dsar/adapter-c15t` import.

**Chat SDK persistence.** SQL-backed Chat SDK state now needs migration
`0003-chat-runtime-lists-and-queues` (`chat_state_list_keys`,
`chat_state_lists`, `chat_state_queues`). Runtimes that already apply ordered
`@dsar/persistence` migrations pick this up on startup. Custom migrators need
to run `0003` before serving Chat SDK traffic.

## Migration steps

1. Install Node.js 24. Confirm with `node --version`.
2. Install `dsar@1.0.0` once it is on npm. Until that publish, stay on `0.0.5`
   or use this git line after `1.0.0` is tagged.
3. If the host imports Effect types or constructs DSAR layers, set `effect` and
   matching `@effect/*` packages to `4.0.0-beta.101`.
4. If the host typechecks DSAR types, set `typescript` to `7.0.2` (or another
   TypeScript 7 release).
5. Search the host for `adapter-c15t` and `dsar/adapter-c15t`. Remove those
   imports. Wire inbound through `dsar/inbound-resend` or `dsar/inbound-slack`,
   or omit inbound adapters until you have a supported channel.
6. If you persist Chat SDK state with `@dsar/persistence-sqlite` or
   `@dsar/persistence-pg`, boot the runtime once so migration `0003` applies, or
   run your usual migrator through the ordered registry.
7. If you use `makeUnkeyBearerResolver`, thrown `verifyKey` failures now return
   no identity and DSAR answers `401`. Attach `onVerifyError` when you need to
   log provider outages. See [Unkey Integration](../integrations/auth/unkey.md).

Optional after the runtime is up:

- Node SDK webhook receiver: `dsar/node-sdk/webhooks` plus Express, Hono, or
  Next adapters. See [SDK and Runtime Modes](../reference/developer/sdk-and-runtime.md).
- Dispatch listing and replay: `GET /webhooks/dispatches`, CLI
  `dsar webhooks list` / `replay` / `replay-all`. See
  [Webhooks API](../reference/api/webhooks.md).
- Operator diagnostics: `dsar doctor`, `GET /status/diagnostics`,
  `client.diagnostics()`. See [DSAR CLI](../reference/developer/cli.md) and
  [Status API](../reference/api/status.md).

## Rollback

Pin `dsar@0.0.5` again and reinstall.

Node 24 can stay. Published `0.0.5` did not declare `engines`, but this git
line already required Node 24.

Chat SDK tables from migration `0003` are not dropped automatically.
Persistence rollback on this tree is forward-only in production. In
development, delete the SQLite file and re-apply migrations. On Postgres, leave
the extra tables or drop `chat_state_queues`, `chat_state_lists`, and
`chat_state_list_keys` only when nothing still reads them.

Rolling back the npm package does not unpin a tenant policy pack. Do not run
policy apply as a substitute for this rollback.
